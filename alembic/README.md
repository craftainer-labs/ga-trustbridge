# alembic/

Database migrations, generated and applied by
[Alembic](https://alembic.sqlalchemy.org/) against `src/app/models`'
SQLAlchemy metadata. Lives at the repo root, alongside `scripts/`,
`tests/`, and `docs/`, not under `src/`: it's a dev/ops tool, not
installable app code — see `src/README.md`'s "Don't put fixtures/sample
data/documentation here".

- `env.py` — imports every `app.models` module (so autogenerate sees
  every mapped model) and runs migrations over the app's own asyncpg
  engine, sourcing the DSN from `app.config.get_settings()` rather than
  `alembic.ini`.
- `script.py.mako` — the template new revision files are generated from.
- `versions/` — one file per migration, named `<revision>_<slug>.py`.

`../alembic.ini` leaves `sqlalchemy.url` unset (see `env.py` above) and
runs every autogenerated revision script through `ruff format`/`ruff
check --fix` via `[post_write_hooks]`, so a generated migration matches
the rest of the repo's style without a manual pass.

See `../src/app/README.md`'s "Alembic migrations" section for how
migrations apply automatically on startup.

## Do

- Generate a new migration after changing `src/app/models`: `uv run
  alembic revision --autogenerate -m "..."`, then read the generated
  file — autogenerate doesn't catch everything (renames, some
  constraint changes) and needs a manual adjustment for those.
- Give a migration file the same `# noqa`-free, ruff-clean bar as any
  other Python file in this repo (already handled by the
  `post_write_hooks` above for the common case).

## Don't

- Hand-edit a `sqlalchemy.url` into `../alembic.ini` — `env.py` already
  sources it from `app.config.get_settings()`, the same settings the
  app itself connects with.
- Edit or delete an already-applied migration in `versions/` — add a new
  one instead, the same as you would with any other database migration
  tool.
